# Agent 目录已有记录的更新同步

当前普通同步用 `(last_activity_at, conversation_id)` 作为整个设备目录的游标。它能顺序扫描已有行，但不能表示每个会话各自的变化：会话 A 的活动时间如果晚于会话 B，B 后续即使产生新消息，只要时间仍早于 A 的游标，就不会再次上报。新增行的 insert-only 队列和一次性补同步只补缺行，不更新云端已有行。

这个问题可以在隔离目录中复现：先同步 A（3 月）和 B（1 月），再给 B 写入 2 月的消息；本地 B 的预览变化，但下一轮普通上报为空。设备时钟回拨、旧事件迟到及不同会话同时运行都可能触发这种顺序。

不能简单地定期重放完整本地行。普通上报允许自定义名称替换已有名称，也可能更新会话链接、状态、预览和归档字段；云端可能在本次设备上报后已经收到用户重命名、恢复归档或另一设备的新数据。insert-only 接口刻意不修改已有行，不能用来更新已有记录。

后续实现需要同时满足：

1. 在账号隔离的本地目录中持久跟踪每个会话的变更，网络失败、进程重启和发送期间再次修改都不能丢失待同步变化。游标必须基于变更序列，而不是跨会话的活动时间。
2. 服务端为已有行提供原子的条件更新：只更新本次确实改变且仍符合上次已确认云端值的字段；用户自定义标题和归档操作保留其独立的优先级与冲突规则。响应返回实际保存的行及冲突结果，不能把输入快照当作云端事实。
3. 对已有安装建立基线时，先获取实际云端行；无法确认过去变更先后顺序的字段不得自动覆盖。对缺失行仍使用现有 insert-only 接口。旧服务端不支持新接口时保留待同步状态，不能降级为无条件重放。
4. 覆盖同时间戳、不同会话的活动顺序、发送中再次修改、超时后请求实际已提交、重启续传、账号切换、云端重命名及归档恢复与设备更新并发等场景。服务端 SQL 必须在真实执行路径上测试；需要新字段时只提交本地迁移 SQL，按既定流程由用户部署。

`reportAgentConversationMetadata` 在服务端返回匹配的目录行时向调用者提供该行，并保持旧服务端空响应兼容。服务端本地代码增加了 `reconcile-previews`：对摘要、首条提示和最后一条消息逐字段做原子条件更新，只允许同账号、当前所属设备操作，返回实际值；它不更新标题、归档或其他字段。

CLI 在本地目录中持久记录安装新版后预览字段的旧值和新值，发送前对两侧使用与正常目录上报相同的脱敏规则。队列按会话保持顺序，每轮最多尝试 50 条；失败或旧服务端不支持接口时保留记录，一个设备归属变化或缺失的会话不会阻塞其他会话。云端值与旧值不一致时保留云端值并结束该条变更，不自动覆盖冲突。重试时云端已是新值也视为成功。

这一机制只覆盖安装新版后发生的三个预览字段变化。安装前已遗漏的更新、状态和会话链接等其他字段仍需要单独设计安全的基线和冲突规则。它也不把已经存在冲突的本地值强行写入云端。

正文同步使用开始与完成清单确认：完成接口确认全部分块后才保存成功检查点；失败和旧服务端不支持接口时保留待重试版本。已经按旧协议同步的本地正文会逐步使用新版本重新核验。应先部署支持清单接口的服务端，再更新 CLI；旧 CLI 仍使用逐块状态语义。
