# 原生终端空闲但 App 消息被拒绝

2026-11-21 在用户当前会话中观察到：`state=idle`、`busy=false`、审批和问题均为零、消息队列为空，然而 `userTyping=true`、`ready=false`。输入框当时显示的是官方 Auto 模式提示，不是用户草稿。此前所有拒绝统一显示 `Antigravity is not ready for this input.`，因此 App 没有给出实际阻塞原因。

已确认的直接原因是本地输入标记滞留。旧实现对 stdin 中的可打印字节做正则匹配；终端焦点通知、设备/光标报告以及方向键也带有字母和数字，会错误地设置该标记。无法从旧日志倒推这个用户会话中究竟是哪一组按键或终端回复首先触发了它，因此没有声称捕获到了原始触发包。

修复使用有状态的终端输入解析器，跨数据块识别 CSI、OSC、设备/光标回复、焦点通知、Shift+Tab 和括号粘贴。真实文本立即保护草稿；原生编辑器的最终回显用于确认历史导航、删除和清空后的草稿状态。Auto、Plan、Accept-edits 三种官方占位提示不算草稿。原生问题面板与权限控制路径保持原有行为。

原生消息拒绝现在保留具体原因，App 对草稿、审批、登录、工作区信任、交互面板、满队列和送达不确定状态显示相应中英文说明。旧协议的其他拒绝文本保持兼容。

验证：

- `tests/agyTerminalInput.test.js`：修复前重现焦点/设备回复、分块序列和清空草稿后的阻塞；修复后通过，并验证真实多行草稿、历史导航和三种占位提示。
- `node scripts/test-agy-terminal-input-live.mjs --live`：在隔离工作区以真实外层 PTY 启动 `originrouter agy`，外层 xterm 自动回复查询，再通过 App 本地 API 发送。消息正常得到官方回答；真实本地草稿阻止远程覆盖；Ctrl+U 清空后再次发送并得到回答，三项通过。
- 上述真实测试观察到 3 次自动终端回复；不是只测试 App 后台无键盘启动。
- `npm test` 全部通过；App 拒绝提示、历史/附件和原生模型相关 22 项测试通过。
- 检查没有改变模型提供方、账户登录、会话身份、Hooks 审批或 Claude/Codex 分派。

当前用户进程已在核对空编辑器、无任务和无阻塞交互后修正输入状态并应用输入解析修复，没有重启进程、修改用户草稿、自动重发消息或执行用户的首页修改任务。后续启动直接使用修复后的源码；App 新增提示需要加载更新后的 App 代码。

本次只接受 macOS ARM64 / 官方 agy 1.5.13。没有把此前审计通过推断为原生终端输入与后台 PTY 所有边界完全覆盖；本例暴露了此前验收对真实外层终端自动回复覆盖不足的问题。
